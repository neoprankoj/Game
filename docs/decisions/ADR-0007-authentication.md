## Context
- Accounts must work identically on web, iOS and Android (one universe). Account data must live **in our PostgreSQL** (source of truth; recoverable from the DB alone). No hand-rolled crypto (`CLAUDE.md` §5).
- Later needs: roles (player/admin, Part 11.6), session revocation, rate-limited login (11.2), account deletion and data export (12.6).

**Verified facts (npm registry and docs, 2026-10-31):**
- `better-auth` latest is **1.7.14** (2026-10-26). There are maintained `release-1.4` and `release-1.6` lines and a `1.8.0-beta`, so the project is actively maintained with backported fixes. `@better-auth/expo` is 1.7.14.
- Better Auth docs:
  - official **Fastify** integration: catch-all `/api/auth/*` route using `fromNodeHeaders`, with `trustedOrigins` and CORS (`credentials: true`) required for cross-origin clients;
  - **Drizzle adapter** with `provider: "pg"` and optional `schemaName` (e.g. a separate `auth` schema). Schema generated by the Better Auth CLI, migrations applied with drizzle-kit;
  - **Expo**: "supports both Expo native and web apps". On native, session data and cookies are kept in SecureStore.
- Auth.js (NextAuth) is now maintained by the Better Auth team (Better Auth announcement, 2025-09-22). `lucia` on npm is marked **deprecated** ("Please see https://lucia-auth.com/lucia-v3/migrate").

## Decision
- **Better Auth 1.7.x** on the server (`apps/api`), mounted as the official Fastify catch-all route. It uses the **Drizzle adapter** (`provider: "pg"`), with its tables in a dedicated Postgres schema **`auth`**. Game tables reference `auth.user.id` from a `player` row; game domains never read auth tables directly.
- **Database sessions** (revocable), not stateless JWTs. Admins can end sessions (11.6), and a compromised device can be signed out.
- Client: `better-auth` React client plus `@better-auth/expo`, using cookies on web and SecureStore on native.
- MVP sign-in: **email + password**, with email verification and password reset via a transactional email provider (chosen in Part 2.8; cost about $0 at playtest scale). Social providers are optional and need the owner's input (see header).
- Roles: a minimal `role` claim (`player` | `admin`) via Better Auth's admin/role capability, or our own `account_role` table. Part 2.8 picks one and records it here.
- Pin to a minor line (`~1.7.x`) and upgrade deliberately, since auth is security-critical. Monitor Better Auth security advisories.

## Alternatives
| Option | Pros | Cons | Verdict |
|---|---|---|---|
| **Better Auth** | TypeScript; data in our Postgres via Drizzle; official Fastify and Expo support; plugins (admin, rate-limit, 2FA) | Young project (2024); fast release cadence means more upgrades | **Chosen** |
| Auth.js | Long history | Next.js-centric; now in Better Auth's hands, which recommends Better Auth for new projects | Rejected |
| Lucia | Simple, educational | **Deprecated** on npm | Rejected |
| Managed auth (Clerk, Supabase Auth, Firebase Auth) | Zero auth maintenance | User data outside our Postgres (breaks rule 4 / recoverability); vendor lock-in; per-MAU pricing | Rejected |
| Hand-rolled sessions with `argon2` | Full control | Violates "no hand-rolled crypto" in spirit; high security risk for one person | Rejected |

## Trade-offs
- We own auth operations (email delivery, breach response) in exchange for keeping all data in our database.
- Better Auth's cookie handling across origins needs care (web client on a different origin from the API). Part 2.8 decides between same-site subdomains (`app.` + `api.` under one domain, the preferred option) and explicit `trustedOrigins`.

## Consequences
- Part 1.3 includes the `auth` schema (owned by the Authentication domain) and the `player` table that links to it.
- Part 2.8 delivers sign-up, sign-in, sign-out and session lookup in Fastify, client screens, and tests for session expiry and revocation.
- Rate limiting of auth endpoints is configured in 2.8 (basic) and hardened in 11.2.
- **Revisit when** Better Auth has a serious unpatched advisory, maintenance stops, or a required feature (e.g. account deletion flows) cannot be implemented cleanly.

## Verification
Part 2.8: integration tests for sign-up, login, wrong password, session revocation and expired session. A test proves a request without a session cannot reach any game route. Manual smoke test on web and one native platform.

## Implementation notes (Part 2.8, 2026-11-02)
- **Versions:** `better-auth` and `@better-auth/expo` **1.7.15**, pinned exactly in the pnpm catalog. The schema generator is now the `auth` package (`@better-auth/cli` is deprecated on npm). `drizzle-orm` 0.45.4 is within Better Auth's peer range.
- **Schema:** `packages/db/src/schema/auth.ts`.
  - Generated with `auth generate` for our options, then adapted: schema `auth`, `timestamptz`, CHECKs for the lowercase email and the role.
  - Migration `0001_auth_schema.sql` is generated by drizzle-kit.
  - Better Auth validates the Drizzle schema at startup, and a test proves the schema and migrations agree.
- **Roles:** a `role` column (`player` | `admin`, `input: false`), not the admin plugin. The plugin would expose admin endpoints, including impersonation, outside our audit log. Suspension fields come with 11.6.
- **Email:**
  - verification is required, which also makes sign-up enumeration-safe;
  - delivery goes through a `Mailer` port: an in-memory version (tests) and a dev mailbox file (local, E2E);
  - production refuses to start until a real provider exists (Part 2.10);
  - the server does not send a link on sign-in (`sendOnSignIn: false`). The client asks for a new link itself, with its own return URL, because a server-sent link would return users to the API host.
- **Security defaults made explicit:**
  - `disableOriginCheck: false` and `disableCSRFCheck: false`. Better Auth turns these checks off when `NODE_ENV=test`, which hid an open-redirect token leak in the first test run. See SECURITY.md T-6.
  - telemetry is off;
  - the library logger is forwarded at `warn` and above (its `info` lines contain email addresses).
- **Rate limits:** Better Auth's limiter with per-path rules (`AUTH_RATE_LIMITS`), in memory (one API instance). The client IP comes from our adapter header, which is set from Fastify's `request.ip`.
- **Fastify mount:** an encapsulated catch-all `/api/auth/*`.
  - The JSON body is forwarded as the raw string;
  - each `Set-Cookie` header is copied separately (the docs' example joins them, which corrupts multiple cookies).
- **Cross-origin choice:** same-site app and API (`app.` + `api.` subdomains in production, `localhost` ↔ `localhost` in development). Cookies stay `SameSite=Lax`, with no third-party cookies.
- **Native:**
  - the Expo plugin stores the cookie in SecureStore and the typed API client sends it;
  - `test/native-client.test.ts` runs the real Expo client plugin against the real API, with only the React Native platform modules stubbed;
  - rendering on a device remains a manual check.
